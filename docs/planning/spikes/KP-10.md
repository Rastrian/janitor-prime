# KP-10 — Cold-parse latency on a large real repo

| | |
|---|---|
| **Kill-point** | PLAN §5 KP-10 · ADR-0007 · risk R15 (eval-2 amendment 3) |
| **Status** | **MEASURED at F1 (2026-09-13) — cost is acceptable; ADR-0007 unchanged, now with numbers** |
| **Code** | `src/spikes/parse_latency.rs` |
| **Data** | `benches/spike-kp10.json` |
| **Commit** | F1 work item 6 |

## Hypothesis under attack

ADR-0007 accepts cold re-parse per CLI invocation as the v0.1 wart
(asserted, never measured — eval-2 §5.3.2). This spike converts it into a
measured decision: if unacceptable, the daemon/warm cache moves up in
priority.

## Setup

Per the F1 brief: **no DSL, no scan** — parse throughput only. Inside the
run: `git clone --depth 1` of rust-analyzer into `/tmp` (removed at the
end, Drop-guarded on error paths too), walk all `.rs` files (skipping
`.git`/`target`), parse each **serially** through the `ffi_shim` boundary
with one parser (the §1.2 one-parser-per-worker shape), one tree at a
time — dropped before the next file, exactly the streaming discipline of
ADR-0007. Timed loop = read + parse (scan's per-file cost); clone
excluded. Release profile.

**Machine context** (recorded in the data file): Intel Xeon E3-1270 @
3.40 GHz, 8 cores, 32 GB RAM, Linux x86_64.

## Results

| metric | value |
|---|---|
| corpus | rust-analyzer @ HEAD, shallow — **1,484 files, 16.7 MB** of Rust |
| wall time (serial read+parse loop) | **2.21 s** |
| throughput | **672 files/s**, 7.54 MB/s |
| peak RSS (`VmHWM`) | **15.3 MiB** |
| files with ERROR/MISSING nodes | 274 / 1,484 (18.5%) |

Five slowest files (parse time only): `crates/syntax/src/ast/generated/nodes.rs` 62 ms / 349 KB · `crates/ide-db/src/generated/lints.rs` 49 ms / 738 KB · `crates/hir/src/lib.rs` 39 ms / 230 KB · `crates/rust-analyzer/src/config.rs` 21 ms · `crates/hir-def/src/expr_store/lower.rs` 20 ms. The slowest are exactly the generated/huge files — latency is size-driven, no pathological cases.

## Findings

1. **Cold parse is cheap at repo scale**: 1.5k files in 2.2 s *serial* with
   one parser — and this is the floor, not the product: `scan` runs the
   same work under rayon (ADR-0007's "rayon makes it tolerable"), so
   wall time on this 8-core box lands well under a second for the parse
   phase. Daemon/warm cache stays post-v0.1 (F10) — the accepted wart is
   now an *informed* wart.
2. **RAM discipline confirmed** (eval-1 F1's OOM concern): peak RSS
   15.3 MiB against a 16.7 MB corpus — flat, not O(repo). The
   parse-then-drop loop is the whole story.
3. **Real repos contain parse errors**: 18.5% of rust-analyzer's files
   leave ERROR/MISSING nodes under tree-sitter-rust 0.24.2 (recent/nightly
   syntax the grammar doesn't know). Not this spike's question, but it
   hardens two design points: `scan` must tolerate per-file errors
   gracefully (report, don't abort), and KP-4's whole-file gate means
   `apply` on such files will surface pre-existing errors — F5's error
   report should distinguish *introduced* vs *pre-existing* counts.

## Verdict

KP-10 closes green: acceptable latency, flat RAM, no priority change.
Reproduce: `cargo test --release --features spikes -- --ignored latency`.
